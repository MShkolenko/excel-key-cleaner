# Changelog

## 3.3 - 2026-09-24

**Отчёт без адресов, выделено только то, на что стоит посмотреть** (решение владельца: на листе
русского текста строка «КИРИЛЛИЦА ОСТАВЛЕНА в 100 555 яч.: E32, F32, …» была шумом).

- В отчёте больше нет адресов ячеек - только числа. Единственное исключение - аварийное сообщение,
  когда не удался откат ячейки с оформлением символов: там адреса нужны, чтобы вернуть ячейки из
  временной книги руками.
- После прогона выделены только **подозрительные** ячейки: латиница и кириллица в одном слове
  (`СЕ.U1`, `07UУQ`, `Cекция`) - похоже на код, за который правило не взялось; с флажком 5 - буква
  без латинской пары. Плюс прежние исключения: заголовки таблиц, объединённые области не целиком,
  rich text, записанный целиком. Куски слова делит `/`, поэтому пары вида `кг/kg` - не подозрительны.
- Русский текст - одной строкой «Русский текст оставлен как есть: N яч.», не выделяется. Если
  подозрительного нет, выделение пользователя остаётся как было.
- Правило замены не менялось: на тех же пяти рабочих книгах изменено ровно столько же ячеек, что и
  в 3.2. Подозрительных там 0,4 % от оставленной кириллицы (6 688 из 1 568 145), и число,
  выделенное макросом, совпало с независимой моделью на Python по каждому листу.
- Стенд: I2 теперь строгий - выделение **равно** набору подозрительных ячеек, в тексте отчёта нет
  ни одного адреса, каждая строка с числом встречается ровно раз с верным числом (на подложенных
  ошибках всех трёх видов падает). Проба переполнения по-прежнему проверяет отдельное аварийное
  окно - переполнение теперь даёт подозрительная ячейка, а не списки адресов. `measure_left.py`
  нагружает выделение подозрительными ячейками.

## 3.2 - 2026-09-24

**Надстройка.** Макрос теперь ставится одним файлом `excel-key-cleaner.xlam`, без редактора VBA:
вкладка **«Очистка ключей»** сразу после «Главной» (кнопки «Очистить ключи» и «Как это работает»)
и пункт «Очистить ключи» в меню правой кнопки по ячейке и по таблице. В диалоге надстроек Excel
она называется «Очистка ключей». Код внутри - тот же, что в 3.1: модули `Cleaning` и
`CleaningForm` плюс маленький `Ribbon` (обработчики кнопок); форма теперь озаглавлена «Очистка
ключей». Установка модулями в `PERSONAL.XLSB` осталась вторым способом.

- `build.py` собирает надстройку сам: отдельный невидимый Excel импортирует модули и сохраняет
  `.xlam`, разметка ленты (`src/customUI14.xml`) вписывается в пакет.
- `tests/verify_xlam.py` проверяет собранный файл так, как его видит Excel: код модулей внутри
  совпадает с `dist/` (тем, что прошёл стенд и рабочие книги; без учёта регистра, который редактор
  VBA выравнивает по проекту, но строки и комментарии - точно), форма - те же элементы, подписи,
  положения и порядок Tab, что даёт обычный импорт `dist/` (побайтно `.frx` не сравнить: Excel
  переписывает в нём счётчики даже при двух одинаковых импортах подряд), проект компилируется,
  связь ленты в пакете и сигнатуры обработчиков точные, значки существуют; в видимом экземпляре
  Excel за пределами экрана лента загружается (`onLoad` срабатывает - значит, Excel принял разметку
  целиком), снимок кладётся в `docs/ribbon.png`. На подложенных ошибках (чужое имя обработчика,
  изменённая строка в модуле, подменённый заголовок формы) проверка падает.
- Сборка атомарна: новая надстройка сначала собирается во временный файл и проверяется, и только
  потом заменяет прежнюю; Excel закрывается на любом пути.
- `docs/INSTALL.md` переписан под надстройку: «Разблокировать» файл из интернета, папка
  надстроек, как сделать её надёжным расположением и чем это оплачивается.

## 3.1 - 2026-09-24

Правило замены омоглифов - **по словам**, а не по ячейке целиком; идея и первая версия - PR #2
(DarthKrya). Окончательное правило выбрано не на придуманных примерах, а на копиях пяти рабочих
книг (1 586 269 текстовых ячеек с кириллицей), и там же найдены и
исправлены три дефекта, которых стенд не видел.

**Правило.** Слово - кусок между пробелами, переносами, скобками, запятыми, точкой с запятой и
кавычками; невидимые символы, дефис, точка и `/` слово не делят. Слово с кириллицей меняется, если
правило кода выполняет само слово ИЛИ вся ячейка (как в 3.0). Русское слово - только кириллица, без
латиницы и цифр, со строчной буквой - не меняется никогда.
- 3.0 превращал `Насос XX.0120.10UMA` в `Hacoc XX.0120.10UMA` и не чинил код рядом с русским словом
  (`Опора XX.0120.10UМА`). 3.1 делает наоборот.
- На рабочих книгах против 3.0: **+3 153** исправления (в основном коды оборудования и зданий внутри
  русских фраз), **−24** (одиночные строчные `о`, `с` и `хар.С`, который 3.0 портил в
  `xap.C` - теперь названы, а не заменены), ни одного нового изменения русского слова со строчной
  буквой. Настоящий макрос совпал с независимым зеркалом на всех текстовых константах этих книг.
- Отвергнуты по тем же данным: решение только по слову, как в PR (терялись ~2 000 верных замен
  английского текста в двуязычных ячейках: `сompressed`, `МPа`); «кодовая часть ячейки целиком»
  (портила `Рр<2,2`, `4-х)`, `(24В)` - собирала латиницу со всей длинной фразы); `/` как граница
  (−230 верных замен координат и осей ради ~25 случаев `4-х/Safety`).
- Невидимые символы слово не делят (в PR делили - код с ZWSP внутри переставал чиниться); строка
  не собирается по символу (в PR - квадратичное время на длинной ячейке): правка на месте через `Mid$`.

**Большие листы - найдено на рабочих книгах, есть и в 3.0:**
- Выделение «не тронутого» собиралось `Union` по одной ячейке - это растёт почти как куб
  (8 000 ячеек - 130 с); рабочий лист с 63 109 такими ячейками шёл 15 минут. Теперь ячейки копятся
  полосами по столбцу, `Union` строится один раз деревом: тот же лист - 10,7 с.
- Проверка выделения сравнивала строки адреса, а Excel при выделении сам сливает соседние области -
  отчёт писал «выделить НЕ удалось» при выделенных ячейках. Теперь проверяется, что каждая область
  лежит в выделении.
- `cell.MergeCells` по каждой ячейке копит GDI-объекты Excel до потолка процесса (10 000); после
  этого `Workbooks.Add` для резервной копии rich text отказывал, и прогон откатывался целиком -
  на двух рабочих книгах из пяти (по 1,6-1,7 млн ячеек) макрос не менял ничего. Теперь `MergeArea.CountLarge`:
  GDI не растёт, проверка 160 с → 1 с. Теперь обе обработаны: 28,5 с и 135,8 с.
- Предел: названные ячейки, из которых ни одна не соседствует с другой (шахматка), собираются в
  выделение сверхлинейно - 100 000 таких ячеек 30 с, миллион займёт минуты. На рабочих книгах
  названные ячейки идут полосами: книга с 502 тыс. ячеек с кириллицей прошла целиком за 28,5 с.

**Тесты.** 54 входные строки × 8 наборов флажков = 432 сверки с зеркалом (новые случаи - из рабочих
книг: скобки `(ПУ АС)(99UXX)`, английское слово с кириллицей, оси, одиночная строчная `с`); 45 проб.
Новый гейт `tests/measure_left.py`: тысячи несоседних ячеек, которые надо назвать и выделить; на 3.0
он падает (×34 по времени при ×4 по объёму), на 3.1 - линейно (20 000 ячеек - 3,7 с).

## 3.0 - 2026-09-22

Переработка по требованию владельца после двух дней эксплуатации: **ни одна текстовая ячейка
выделения не остаётся необработанной молча**. Сделано двумя независимыми решениями (Claude и
Codex), сверено, затем второй круг Codex по итоговому коду. Что изменилось в поведении:

- Ячейки с разным оформлением символов (rich text) **чистятся**, оформление каждого символа
  сохраняется: правки применяются посимвольно через `Range.Characters` справа налево (все
  преобразования макроса - замена 1:1 или удаление, вставок нет). Откат для таких ячеек - точный:
  до первой записи ячейка копируется во временную скрытую книгу и при ошибке копируется обратно.
- Скрытые и отфильтрованные ячейки **обрабатываются** (в отчёте - сколько их было).
- Всё, что макрос не тронул, **называется по адресу и выделяется на листе** после прогона:
  кириллица, оставленная по правилу "похоже на код"; объединённые области, выделенные не целиком;
  rich text, где посимвольная правка не сошлась и ячейка записана целиком.
- Новый флажок **5. "В выделении только коды: кириллицу менять везде, без проверки"** -
  явный способ снять правило, когда пользователь знает, что в выделении только ключи. Буквы,
  которым нет латинской пары (Ж, Ш, У, Ы...), остаются и тоже перечисляются.
- Отчёт показывает полный учёт выделения: сколько ячеек всего, текстовых, формул, чисел и дат,
  логических/ошибок, пустых - чтобы было видно, куда делась каждая.
- Ошибки не глотаются: "текстовых ячеек нет" принимается только если независимый счёт
  (`CountA` минус формулы/числа/прочее) тоже даёт ноль; иначе - настоящая ошибка наверх. Ошибка
  чтения свойств шрифта не пропускает ячейку, а направляет её на посимвольный путь.
- Заголовки таблиц Excel не переписываются (Excel сам переименовывает дубликаты и правит
  структурные ссылки в формулах вне выделения) - они перечисляются как исключение; тело таблицы
  чистится.
- Каждая обычная запись перечитывается: если Excel положил в ячейку не тот текст или не текст -
  это ошибка с откатом, а не тихий успех. Откат тоже перечитывает каждую возвращённую ячейку;
  если вернуть rich text не удалось, резервная книга с исходными копиями остаётся открытой и
  названа в сообщении.
- Выделение исключений делается при выключенных событиях и ПРОВЕРЯЕТСЯ; "выделены" в отчёте
  появляется только по факту, иначе - список адресов и честное "выделить не удалось".
- `Ctrl+Break` во время записи ведёт в откат (`EnableCancelKey = xlErrorHandler`), а не
  оставляет книгу полуправленной.
- Переносы строк: добавлены NEL (U+0085), вертикальная табуляция (11), разрыв страницы (12).
- Измерено на Excel 2024 и учтено в коде: `Range.Characters` нумерует символы с `CRLF` как одним
  символом (и после любой правки убирает `CR`); правки через `Characters` на тексте длиннее **255**
  символов - молчаливый no-op. Поэтому rich text до 255 символов правится на месте, длиннее -
  записывается целиком и перечисляется в отчёте. Формулировка "оформление сброшено" была неверной
  и исправлена в 3.0: замерено, что целая запись НЕ сбрасывает разметку символов - Excel оставляет
  её по позициям, то есть после сдвига текста она может оказаться на других символах.
- Путь отката **выполнен на стенде**, а не только прочитан: в тестовую копию модуля внедряется
  ошибка записи (`tests/gen.py --fail-at=B5`, тот же механизм, что заглушка формы); к этому
  моменту уже изменены rich-ячейка и объединённая rich-область - обе вернулись из резервной копии
  с оформлением и объединением, упавшая ячейка и следующая за ней не тронуты, временная книга
  закрыта, состояние Excel восстановлено, сообщение честное.
- Ячейка из одних пробелов/невидимых символов очищается до пустой - это допустимый результат
  записи, не ошибка (третий круг Codex, A). Табуляция и перенос строки, если их действие
  выключено, остаются на месте вместе с оформлением (B). После цикла записи ошибка уже не ведёт
  к откату, резервная книга закрывается последней, неудача закрытия называется в отчёте (C).
  `Ctrl+Break` внутри посимвольной правки доходит до общего отката. Отчёт укорачивает списки
  адресов ступенями и никогда не режет предупреждения.
- Оформленная ячейка с `CRLF` при выключенной замене переносов больше не пишется целиком ради
  сохранения `CR`: правится посимвольно, перенос остаётся, а `CR`, который Excel сам убирает при
  любой правке через `Characters` (измерено), считается и называется в отчёте отдельной строкой
  (четвёртый круг Codex).
- В серии пробельных символов исходный символ с оформлением сохраняется, даже если перед ним
  несколько чужих: `A<TAB><TAB><подчёркнутый пробел>B` схлопывается в `A B` с подчёркнутым
  пробелом, а не с пробелом, доставшимся от первой табуляции (четвёртый круг Codex).
- Ошибка (или `Ctrl+Break`) ПОСЛЕ последней записи больше не оставляет Excel в рабочем режиме
  макроса: управление уходит на свой обработчик одной инструкцией, окна без обработчика нет.
  Откатывать там уже нечего - ячейки записаны и перечитаны, - но резервная книга закрывается,
  состояние Excel возвращается, а сама ошибка НАЗЫВАЕТСЯ в отчёте (четвёртый круг Codex, блокер).
- Восстановление состояния Excel проверяется: каждое из четырёх свойств пишется и перечитывается,
  и всё, что вернуть не удалось, попадает в отчёт отдельным предупреждением вместо молчания.
- Предупреждения (`CRLF -> LF`, незакрытая резервная книга, невосстановленное состояние) входят в
  бюджет отчёта наравне с адресами и не отбрасываются; отбрасывается только блок статистики.
- **Пробелы и невидимые символы по краям ячейки убираются ВСЕГДА**, независимо от флажков
  (владелец, 2026-09-22): ведущий пробел в ключе - всегда мусор, а глазами его не видно. Одно
  исключение: если замена переносов строк выключена, перенос по краю остаётся - его оставили
  намеренно. Из действия 4 «обрезать края» убрано, оно больше не его работа.
- Прогон БЕЗ единого флажка больше не отказ: он чистит края (они чистятся всегда) и говорит об
  этом в отчёте. Отказаться от прогона - кнопка «Отмена». Раньше макрос выходил с «Вы не выбрали
  ни одного действия», и обязательная очистка краёв в этом случае не срабатывала вовсе.
- Перенос строки по краю, который велено сохранить, больше не прикрывает соседний обычный пробел:
  `{LF} AB` -> `{LF}AB`. Обход края идёт сквозь всю пробельную серию.
- **Убрано второе имя макроса.** `Замена_Кирилицы_С_Выбором` был псевдонимом той же процедуры, и
  макрос показывался в списке Excel дважды (владелец, 2026-09-22). Точка входа одна: `CleanKeys`.
  Кнопке, назначенной на старое имя, нужно один раз переназначить макрос.
- **Исправлена ошибка, которая жила с самого начала:** BOM (U+FEFF) не считался пробельным
  символом. Причина - `&HFEFF` в VBA это Integer СО ЗНАКОМ, то есть -257, а не 65279, и
  `Select Case` никогда не совпадал. Нужен суффикс Long: `&HFEFF&`. Нашлось только когда края
  начали чиститься всегда: `XX.ABC <BOM>` оставался нетронутым целиком, потому что обход края
  упирался в BOM и останавливался.
- Аварийные предупреждения (ошибка после записи, незакрытая резервная книга, невосстановленное
  состояние Excel) стоят В НАЧАЛЕ отчёта, а не в конце: `MsgBox` обрезает хвост, и именно там они
  уезжали за обрез. Если отчёт всё равно не помещается, этот блок показывается отдельным окном
  ПЕРВЫМ (пятый круг Codex).
- Каждое аварийное предупреждение ограничено по длине (200 / 60 / 120 символов): описание ошибки
  от Excel бывает в тысячу символов и вытесняло из окна два следующих предупреждения - то есть
  ровно то, что пользователю надо сделать руками (шестой круг Codex).
- Стенд стал ГЕЙТОМ: `Expect` - 60 автоматических проверок значений, падение пробы или сломанный
  инвариант дают `exit 1`; `verify.py` тоже возвращает ненулевой код при расхождении. Матрица -
  37 входных строк x 8 наборов флажков = 296 сравнений, включая набор БЕЗ единого флажка (его
  отсутствие и скрывало дыру с обязательной очисткой краёв). Раньше проба печатала `OK`, если блок не бросил исключение, независимо
  от того, что оказалось в ячейке, и процесс завершался нулём (замечание Codex о самом стенде).
  Гейт в первый же час поймал две ошибки в моих собственных утверждениях.
- Честные цифры скорости (замер без диалогов, см. AUDIT-v3): 40 000 ячеек - 39,1 с на 2.2
  (`Collection`), 3,9 с на 2.4 (массивы), 8,8-11,7 с на 3.0 в пяти замерах за день (A/B последней
  правки в одном состоянии машины: 10,1 с до, 9,7 с после) - плата за контрольное чтение каждой
  записанной ячейки; рост линейный. Прежние "61 с -> 7,5 с" включали ожидание клика по диалогу
  и были неверны.

## 2.4 - 2026-09-22

Исправление собственного фикса из 2.3: `ThemeColor`/`ThemeFont` убраны из проверки rich text.
Оказалось, они бросают ошибку не только на реально смешанной по символам ячейке, а на ЛЮБОЙ
ячейке с обычным, вручную заданным (не через тему) цветом шрифта - даже когда цвет один и тот
же на всю ячейку. В проекте, где цвет шрифта - это данные (например "минус зелёным" в дельтах),
это означало бы пропуск большинства крашеных ячеек, а не только настоящего rich text.
Проверено предметно: ячейка с однородным `ColorIndex=3` - раньше пропускалась целиком, теперь
исправляется; ячейка с реально смешанным оформлением (жирный только первый символ) - как и
раньше, пропускается. Остальные признаки rich text (Bold/Italic/Size/Name/Underline/
Strikethrough/Superscript/Subscript/FontStyle/TintAndShade) не пострадали - они действительно
возвращают Null на смешанном оформлении, не бросают исключение на обычном.

## 2.3 - 2026-09-22

Первый после публикации отчёт от пользователя (operator, живая книга) и первый GitHub issue:

- **Падение "Invalid procedure call or argument" в `IsRichText`.** На обычной новой книге все
  свойства шрифта ведут себя штатно, но на реальной, годами редактируемой книге `Font.ThemeColor`
  бросает настоящую ошибку (не `Null`) на ячейке с явным (не привязанным к теме) цветом шрифта
  - воспроизведено отдельно (`.Font.ColorIndex = 3` на новой книге даёт ту же ошибку). Раньше
  ошибка обрывала весь макрос посреди диапазона. Теперь любая ошибка при чтении свойств шрифта
  считается "нельзя определить чисто" и ячейка пропускается - та же логика, что и для настоящего
  rich text.
- **GitHub issue #1** (независимая переработка того же макроса, 5 замечаний; разобрано вместе с
  Codex, каждый - независимо от текста issue):
  - подтверждено и исправлено: `Collection.Item(i)` по позиционному индексу - известная в VBA
    O(n)-операция, из-за которой запись и откат плана были на практике заметно хуже линейного на
    больших выделениях. Заменено на четыре динамических массива с удвоением ёмкости. Измерено на
    стенде: 20 000 ячеек 10.7с -> 3.5с, 40 000 ячеек 61.3с -> 7.5с, рост времени стал практически
    линейным (было x5.7 на x2 объёма, стало x2.16);
  - принято в изменённом виде: вместо чисел в окне - индикация хода через `Application.StatusBar`
    (реже, чем на каждой ячейке, без `DoEvents`, чтобы не открывать повторный вход в макрос);
  - принято: `Option Compare Binary` явно в начале модуля - замена омоглифов зависит от регистра;
  - отклонено как отдельная фича, не как часть этого патча: журнал на отдельном листе - меняет
    книгу за пределами выделения, нужен свой план/откат;
  - не требовало исправления: `U+2028`/`U+2029` уже обрабатывались как переносы строк.
  - предложение по `Area.Value2` (пакетное чтение вместо поячеечного) сознательно не взято в этот
    патч - отдельная оптимизация с более высоким риском (нужно разбирать многообластные и
    многостолбцовые `Areas`), а замена контейнера уже дала основной эффект.
- Символ-галочка (`ChrW(&H2713)`) в итоговом отчёте показывался как `?` в реальном `MsgBox`
  (тот же класс проблемы, что раньше был с подписями формы, только на уровне диалога, а не формы)
  - убран, отчёт теперь на обычном ASCII (`-` вместо галочки).

## 2.2 — 2026-09-22

Второй круг Codex по v2.1 (пять замечаний, четыре приняты, одно отклонено измерением):

- обработчик ошибок взводится ДО смены `ScreenUpdating`/`EnableEvents`/`Calculation` — смена
  режима пересчёта может упасть (книга с OLAP-источником), и состояние Excel должно вернуться;
  восстановление каждого свойства — отдельно, под своим `On Error`;
- откат покрывает и ячейку, на которой упала запись (три операции внутри `PutText`), и
  возвращает прежний числовой формат; сообщение честно различает «ничего не изменено»,
  «возвращено поячеечно» и «N ячеек вернуть не удалось, проверьте вручную»;
- проверка rich text: добавлены `Superscript`, `Subscript`, `FontStyle`, `ThemeColor`,
  `TintAndShade`, `ThemeFont`;
- правило «похоже на код» ужесточено: нужна цифра, и латинских букв не меньше кириллических —
  `МОСТ-A`, `ВЕТЕР A`, `СОРТ-A1` больше не трогаются; `СЕ.U1` тоже (задокументированная цена);
- выделение режется по `UsedRange` перед `SpecialCells`;
- `U+2028`/`U+2029` — переносы строк, `U+1680` — пробел; подписи статистики точнее.
- Отклонено: обход `SpecialCells` по областям из-за предела 8192 — на Excel 2024 измерено
  10 000 областей без ошибок; требование «Excel 2010+» вынесено в README.

## 2.0 — 2026-09-21

Переписано по итогам аудита (см. `docs/AUDIT.md`):

- обрабатываются только видимые текстовые константы (`SpecialCells`), с обходом расширения
  `SpecialCells` на одиночной ячейке;
- запись через формат `@` — текст не перепарсивается в число/дату/формулу;
- замена кириллицы только в строках, похожих на код (есть латиница, вся кириллица — омоглифы);
  добавлены строчные `а е о р с х`;
- табуляция и неразрывный пробел считаются пробелом; нормализация обрезает края;
- план изменений до первой записи, проверка защиты листа до записи, откат при ошибке,
  восстановление `ScreenUpdating`/`EnableEvents`/`Calculation`;
- форма fail-closed: продолжение только по `Tag = "OK"`, `QueryClose` для крестика,
  `Default`/`Cancel` для Enter/Esc;
- rich text пропускается; честная статистика с отдельным счётчиком изменённых ячеек;
- `Long` вместо `Integer` (переполнение на 32 767 символах).
